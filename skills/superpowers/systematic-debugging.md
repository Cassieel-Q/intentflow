# systematic-debugging

## 用途

把 `systematic-debugging` 吸收到当前工作区，用于后端启动、构建失败、测试失败、接口联调失败和前端页面异常。

核心目标：先复现，再定位，再最小修复，不靠猜。

## 铁律

```text
没有根因证据，不提修复方案。
```

## 触发场景

- 后端服务启动失败。
- Maven / npm / Gradle 构建失败。
- 测试或 E2E 失败。
- 页面白屏、接口 4xx/5xx、console error。
- 同一个问题重复修了两次仍不稳定。
- 本地环境、依赖服务、配置、数据库、缓存或消息队列疑似异常。

## 四步法

1. 复现：拿到稳定触发方式、命令、退出码、错误摘要和关键日志。
2. 定位：看最近 diff、配置、依赖、调用链和相似可工作的实现。
3. 假设：只提出一个能被验证的根因假设。
4. 修复：一次只改一个主要变量，修完跑原失败场景和相关回归。

## 禁止事项

- 没复现就改代码。
- 一次改多个可能原因。
- 只修症状，不解释根因。
- 重复同一个失败尝试。
- 把环境失败说成代码通过。

## 三次失败规则

同一问题连续三次修复失败，停止继续试补丁，改为输出：

```text
已复现场景：
已排除项：
当前最可能根因：
为什么继续试补丁风险高：
需要用户或主会话确认的事项：
```

## 持久化

只有稳定、可复用的排障结论需要写入文档：

- 启动命令、profile、端口、依赖服务：`build-command-matrix` 或启动前提文档。
- 反复出现的坑：对应项目 `README.md` 或 `module-map.md`。
- 跨仓边界或架构原因：需求专题或 superpower。

一次性错误日志、临时试算、中间猜测不持久化。
