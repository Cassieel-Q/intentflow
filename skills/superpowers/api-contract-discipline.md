# API Contract Discipline

## 目的

约束前后端接口字段、状态展示、错误提示和表单校验，减少“后端有数据、前端靠猜”的问题。

## 通用规则

- 业务 API 优先返回统一结构：`code`、`message` / `msg`、`data`、必要时 `traceId`。
- 可预期业务失败和校验失败，要返回直接、用户可理解的中文提示。
- 技术异常、网关失败、超时、非 JSON 响应，才由前端使用通用兜底文案。
- `traceId` 只用于排查问题，不作为业务数据、缓存 key 或用户可编辑字段。

## 状态 / 类型 / 枚举

- 后端业务契约字段如果要展示中文名，优先返回 `xxxName`。
- 前端展示业务状态、类型、阶段时，优先渲染后端 `xxxName`。
- 前端可以基于原始 enum/code 做 UI-only 映射，例如颜色、图标、按钮可见性。
- 前端不要把核心业务中文名硬编码成唯一真源。

## 错误提示

- 前端请求封装优先展示后端 `message` / `msg`。
- 页面层避免和请求封装重复 toast。
- 上传大小、类型不支持、解析失败、业务冲突等是业务/校验错误，不要包装成网络错误。

## 表单校验

- 前端应先校验必填、长度、结构、文件大小、不可点击状态。
- 后端仍必须执行同样的强校验。
- 前后端错误文案应尽量一致，避免同一错误在不同端出现两种说法。

## 子会话执行要求

- 涉及接口新增/变更时，后端子会话要给出字段契约。
- 前端子会话要确认调用方是否依赖旧字段。
- 主会话负责在跨仓库之间同步字段名、状态值、错误文案和兼容策略。
