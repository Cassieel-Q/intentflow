# tdd-red-green-refactor

## 用途

把 `test-driven-development` skill 吸收到当前工作区的分级验证体系中：高风险行为先 Red，再 Green，再 Refactor。

它不是要求所有改动都严格 TDD，而是把最容易出事故、最贵的行为优先测试化。

## 铁律

```text
强制 TDD 的行为：先写会失败的测试，再写生产代码。
不能用“最后补测试”冒充 TDD。
```

如果已经写了生产代码但没有对应测试，处理方式是：

- 强制 TDD 范围内：补 Red 证据或回退到可验证步骤。
- 非强制范围内：记录降级理由、执行最低验证，不把它声称为 TDD。

## 强制 TDD 场景

- 金额、库存、订单状态、桌位可用性、容量匹配。
- 权限、身份、租户隔离、业务归属。
- 数据同步、幂等、重试、超时、失败补偿。
- 后端持久化、事务、异步、调度和跨 Bean 协作。
- Bug 修复能用测试稳定复现时。

## 前端策略

- 纯逻辑、状态映射、格式化、校验：优先单元测试或组件测试。
- 页面路径、表单、弹窗、列表状态、订单提交等用户可见行为：结合 `frontend-reuse-and-path-verification`，优先覆盖关键路径。
- 微信小程序原生能力、登录、手机号、支付、定位、订阅消息：能抽成 adapter 的逻辑优先单测；平台真实能力用 H5 mock、微信开发者工具或人工验证补证据。

## 降级场景

以下场景可不强制 Red/Green，但必须记录原因：

- 纯文案、简单样式、小布局。
- 旧仓库没有测试基础，且本次补测试入口成本明显超过改动本身。
- 依赖外部服务或设备环境，本地无法稳定复现。
- 临时调查、只读验证、文档整理。

## 测试产物留存规则

TDD 过程中产生的测试必须在提交前分类：

- 长期保留：表达业务契约、状态机、权限、排序过滤、字段适配、表单校验或回归复现的测试，随代码进仓库。
- 阶段性保留：服务联调、mock 契约、最小页面流程等测试，可以进仓库，但文件名、注释或测试描述要说明阶段用途，真实接口稳定后再转正式测试或删除。
- 临时丢弃：探针测试、一次性复现脚本、截图调试脚本，不进最终提交。若临时落到工作树，必须显式标记 `TEMP_TDD`、`SCRATCH_TEST`、`TEMP_TEST`、`临时测试` 或 `探针测试`，并在提交前清理。

提交前检查：

```sh
./scripts/check-temporary-test-artifacts.sh <repo-path>
```

若检查命中，必须删除临时产物，或把它改造成长期/阶段性保留测试并移除临时标记。

## 子智能体汇报格式

```text
TDD 级别：
测试目标：
Red 证据：
Green 证据：

```
