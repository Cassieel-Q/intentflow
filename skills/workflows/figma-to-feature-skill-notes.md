# Figma 到真实功能的 Skill 评估笔记

## 核心结论

已创建工作区级基准 skill：

- [figma-to-real-feature](../.codex/skills/figma-to-real-feature/SKILL.md)

从 Figma 到真实前后端功能，最消耗 token 的不是“看设计稿”，而是把设计稿和现有代码体系对齐：

- 找现有页面、组件、样式 token 和交互模式。
- 找接口、字段、枚举、权限和状态流转真源。
- 处理各种页面状态：加载、空态、错误、权限、禁用、响应式、长文本。
- 实现后用浏览器验证、失败截图、日志和代码审查反复收敛。

因此，Figma 不能作为唯一真源。更合理的基准 skill 应把 Figma 当作设计输入，把项目代码、接口和验证结果当作落地真源。

## Token 消耗分布

| 环节 | Token 消耗 | 原因 | 适合人工介入吗 |
| --- | --- | --- | --- |
| 读取 Figma 设计上下文 | 中 | MCP 返回节点树、样式、文本、截图描述，复杂页面会很长 | 适合人工先指定 frame/node，避免全文件扫描 |
| 盘点现有前端组件和样式 | 高 | 需要读相似页面、组件库、路由、store、API 封装、样式约定 | 很适合人工提供“参考页面/组件路径” |
| 从设计拆功能范围 | 中高 | 要判断哪些是纯 UI，哪些需要数据、权限、状态、后端接口 | 适合人工先写主流程和边界 |
| 找后端接口与字段真源 | 高 | 需要跨前端 API、后端 Controller/Service/VO/Enum/数据库对象 | 很适合人工提供接口文档或字段说明 |
| 生成实现计划 | 中 | 要把 UI、接口、状态、验收标准串起来 | 可交给 Codex，但最好先有人类确认 |
| 实际编码 | 中 | 如果前面真源清楚，编码反而不是最贵 | 一般交给 Codex 更划算 |
| 调试构建/类型错误 | 中高 | 取决于项目依赖、历史包袱、错误数量 | Codex 适合做，人工只需在阻塞时介入 |
| Playwright/浏览器验证 | 高 | 需要启动项目、登录、构造数据、截图、看 console/network | 人工提供测试账号和路径会大幅省 token |
| 像素级还原比对 | 很高 | 需要反复截图、比对、微调，且收益不一定高 | 只有高价值页面值得做 |
| 代码审查与修复 | 中高 | 需要读 diff、读上下文、验证风险 | 高风险功能值得做 |

## 最值得人工做的事

人工介入最省 token 的位置：

1. 指定 Figma 的具体 frame/node，不要让 agent 在整个 Figma 文件里找。
2. 指定代码里的参考页面，例如“按这个列表页/表单页的模式做”。
3. 给出接口真源：接口文档、字段含义、枚举、权限点、后端负责人确认过的字段。
4. 明确主流程：入口、用户操作、成功结果、失败结果。
5. 提供测试账号、测试数据、登录方式和目标路由。

## 不建议人工做的事

- 不建议人工把 Figma 每个样式值手抄给 agent；让 MCP/截图承担即可。
- 不建议人工手动写大量代码骨架；更应该提供参考实现和边界。
- 不建议追求全页面像素级 1:1，除非这是核心营销页或高优先级验收项。

## 推荐基准 Skill 方向

建议做一个通用型 `figma-to-real-feature` 基准 skill，流程是：

```text
Figma frame/node
→ 设计上下文与截图
→ 现有页面/组件/tokens 映射
→ 前后端接口与字段真源确认
→ 功能范围与状态清单
→ 实现
→ 浏览器验证
→ 代码审查
```

外部可参考：

- Figma MCP 官方能力
- `agent-compass/figma-mcp-frontend`
- `HowardTangOvO/Figma-Context-MCP-Skill`

本地可结合：

- `frontend-design`
- `webapp-testing`
- `requesting-code-review`
- `comet`
- `grilling` / `grill-me` 式追问能力

## 新页面与旧代码改造的分流策略

如果一个 Figma 里同时包含“全新功能”和“基于原有代码改造”的部分，不能用同一套落地策略硬推。基准 skill 应在开始阶段先做分流：

```text
Figma 节点/页面
→ 判断是 new build 还是 existing retrofit
→ new build 走新页面/新组件落地策略
→ existing retrofit 走现有页面差异改造策略
→ 共享接口、权限、字段、状态和组件规范统一收口
```

两类工作的差别：

| 类型 | 优先真源 | 风险 | 推荐做法 |
| --- | --- | --- | --- |
| 全新功能 | Figma + 产品流程 + 后端接口 | 容易脱离现有系统风格，接口真源不清 | 先定路由、页面职责、接口契约和组件复用边界，再编码 |
| 旧代码改造 | 现有代码 + 当前线上行为 + Figma 差异 | 容易破坏已有流程、权限、数据兼容和用户习惯 | 先做差异清单，只改 Figma 明确要求的变化，保留旧流程可用性 |

因此，最终方案不能只叫“Figma 到代码”，而应该叫“Figma 到真实功能”，并且强制包含：

- `新建/改造` 分类。
- 现有页面影响面确认。
- 与旧行为的差异清单。
- 可复用组件和必须新建组件清单。
- 前后端接口是否已有、是否需要新增、是否需要兼容旧字段。
- 按页面或业务闭环拆成多个小任务，避免一个 Figma 一次性吞完整实现。

人工最值得介入的是先在 Figma 或需求文档里标注：

- 哪些页面/模块是全新的。
- 哪些页面/模块是在旧页面上改。
- 旧页面对应的路由或源码路径。
- 哪些旧行为必须保留。
- 哪些旧行为被 Figma 明确替换。

## 是否适合搭配 grill-me

适合，而且建议把 `grill-me` 作为 Figma 落地流程里的“决策澄清器”，但不要让它替代 Figma 解析、代码检索、实现或验证。

最佳分工：

| 能力 | 职责 |
| --- | --- |
| Figma skill | 读取指定 frame/node，提取设计结构、文案、布局、状态和视觉约束 |
| frontend-design | 把 Figma 映射到项目已有组件、样式 token、交互规范和响应式策略 |
| grill-me / grilling | 只在代码和 Figma 都无法决定时，向用户问一个会影响功能结果的问题 |
| comet | 编排计划、实现、验证和持久化 |
| webapp-testing | 用真实浏览器验证页面、表单、弹窗、路由、状态和响应式 |
| requesting-code-review | 对高风险或共享层改动做代码审查 |

`grill-me` 的使用原则：

- 先由 agent 查 Figma 和代码，不要一开始就把问题抛给用户。
- 只问会改变用户可见行为、业务边界或验收标准的问题。
- 每次只问一个问题，给出推荐项和依据。
- 用户回答“不知道”或明确要求 agent 自己判断时，agent 要基于现有证据选择默认方案，并把假设写入文档/计划。
- 不要用 `grill-me` 问实现细节、文件放哪、怎么命名这类 agent 可以自己决定的问题。

针对用户偏好的补充规则：

- 用户不一定知道参考页面、接口、字段、状态或测试数据。
- 遇到这些信息缺失时，应先问用户，并提供可选项。
- 如果用户说不知道，或明确要求 agent 自己做，就由 agent 继续检索代码、Figma 和运行环境，自行形成默认判断。

## 前端组件复用/新建审批门禁

有必要加入“写新前端代码前，先统计哪些页面复用哪些组件、哪些组件需要新设计，并汇报给用户审批”的限定，但建议不要做成所有前端改动都强制阻塞。

推荐规则：

- 必须汇报并等待审批：新增可复用组件、改动共享组件、新增视觉模式、明显重解释 Figma 设计。
- 可以直接继续：页面局部组合代码、复用现有组件的小改动、不会沉淀为公共模式的一次性局部 markup。
- 如果用户已经明确授权 agent 自主判断，则记录组件报告和推荐方案后继续，不再额外阻塞。

这个门禁的价值：

- 防止重复造组件。
- 防止把 Figma 单页风格误扩散成全项目规范。
- 防止旧页面改造时破坏已有组件行为。
- 让用户在高影响的 UI 架构决策前有审批点。
