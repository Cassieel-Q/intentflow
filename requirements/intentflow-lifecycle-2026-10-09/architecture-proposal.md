# IntentFlow 产品全流程架构方案

状态：产物默认格式已确认；内容层与评审运行层第一版已建立，正在做独立需求端到端验证。

## 核心结构

```text
需求入口
  ├─ 关键决策缺口 → personal-grill-me
  ├─ 证据缺口 → demand-evidence-research
  └─ 足够清楚 → 下一产物
       ↓
需求文档 → 原型/设计与流程 → 功能验收 → 数据复盘
       ↘ 每阶段更新同一需求目录的决策、来源、验收和交接记录
```

每个模块有自己的触发条件和退出条件，不能因为上一模块存在就强制运行。产品决策由用户确认；助手可以提供推荐和记录假设，但不能把推荐写成已确认范围。

## 需求目录契约

现有的 `source.md`、`decisions.md`、`open-questions.md`、`acceptance.md`、`grill-log.md` 继续保存来源与决策。后续产物按需放入 `research/`、`prd/`、`design/`、`flows/`、`qa/`、`analytics/`；每个子目录保存自身文件、版本和验证结果。产物清单写在需求目录入口文件中，同一个需求不因进入新阶段再创建平行目录。

## 内容层与运行层

**内容层**由多个简短 skill 和模板构成：需求研究、PRD、原型/流程、验收、数据分析。它们规定输入、应做的判断、记录形状、验收条件和停止点，不内嵌一大段浏览器服务实现。

**运行层**由本地脚本提供：结构校验、静态预览、真实浏览器截图、受控保存、图片复制、缓存与诊断。脚本只处理当前工作区中的允许路径，使用原子写入和版本比对保护用户编辑；截图清理依赖产物归属清单。运行层可在没有安装浏览器截图依赖时明确降级，而不是声称导出成功。

**设计层**优先沿用 IntentFlow 已有的 Figma 构建与代码落地链路。需要快速评审交互时可生成独立 HTML 原型；其他设计工具可作为可选适配，不进入所有需求的必备步骤。多种产物并存时，检查界面、状态和文案的一致性。

## 产物策略

Markdown 是 PRD、验收清单和数据报告的正式记录；交互式 HTML 是按需生成的评审视图。生成的 HTML 要带正式文件的路径与内容版本。浏览器修改只能通过受控回写更新 Markdown，或生成可审查的待合并变更；若版本已变化，拒绝静默覆盖并展示冲突。原型和流程图可以有独立的 HTML/图形文件，但其对应的业务规则仍以需求决策和 PRD 为准。

## 交付顺序

1. **内容闭环**：路由、研究、PRD、验收、分析的模块规则与可核查模板。
2. **表达闭环**：原型、业务流程、页面跳转、状态/时序图，并与 Figma 链路校对。
3. **交互闭环**：浏览器预览、编辑、复制、保存、截图导出、缓存与安全边界。
4. **运行闭环**：跨平台初始化、诊断、更新保护和需求级交接。
5. **端到端验证**：使用一个需求从输入走到验收；尚未存在的上线数据只用于明确标注的格式演示。

每个闭环独立验证后才宣称完成；尚未实现的能力在能力地图中保持“待建立”。
