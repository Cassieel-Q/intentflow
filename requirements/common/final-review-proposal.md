# 最终验收前终审适用性确认

每个 requirement 进入最终验收前，主会话都必须主动向用户发起一次“终审适用性确认”。

这项规则要求主会话主动提出建议，但不强制每个需求都执行完整终审。是否执行专项终审、采用何种深度，由用户根据主会话提供的风险判断作出决定。

## 主会话提议内容

主会话至少说明：

```text
需求：
复杂度 / 风险：
是否涉及状态机、数据库、权限、跨仓库或重要副作用：
推荐：完整终审 / 轻量终审 / 不做专项终审
理由：
预计成本：
请用户决定：
```

用户作出选择前，主会话不得自行启动成本较高的完整终审。

## 可选深度

### 完整终审

适用于涉及状态机、数据库、权限、跨仓库契约、重要副作用或大范围业务改动的需求。通常包括：

- 基于本期完整 Git diff 核对实际改动范围。
- 还原端到端业务流程。
- 展示状态机、操作者以及允许和禁止的状态转换。
- 核对权限、数据库写入和外部副作用。
- 对比最终需求、设计审批和实际实现的差异。
- 汇总测试、冒烟、未验证项和剩余风险，交由用户人工确认。

### 轻量终审

适用于范围有限、风险可控，但仍需要一次整体确认的需求。通常包括：

- 本期实现能力和关键改动文件。
- 主要业务流程。
- 关键风险、验证结果和未覆盖项。
- 只有确实存在状态流转时才展示必要的简化状态说明。

### 不做专项终审

适用于低风险样式、文案、局部无状态改动等简单需求。

- 不额外开展完整代码与业务分析。
- 仍需执行该改动正常要求的构建、测试或人工验收。
- 在 requirement 待办中记录用户选择即可。

## Requirement 待办

每个 requirement 都应保留以下待办，直到用户作出选择：

```text
- [终审适用性确认] 最终验收前由主会话主动评估并向用户建议完整终审、轻量终审或不做专项终审；具体是否执行及深度由用户决定。
```

该待办表示“必须主动提议并取得用户选择”，不表示“必须执行完整终审”。
